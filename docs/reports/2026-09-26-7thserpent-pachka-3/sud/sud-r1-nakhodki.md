### P3-R1-MARSHRUT-1 | дефект

**Что не так.** Обещание комментария «`sizes` "после" не меньше "до" на любом окне — браузер берёт
кандидата не меньше прежнего, растяжение не растёт нигде» выполняется только в браузере, который
разбирает математические функции в атрибуте `sizes`. Safari до 26.4 (выпущен 24.03.2026) разбирает
в `sizes` только `calc()`. Длина каждой из трёх записей — `max(…)`, поэтому там все три записи
отбрасываются, и `sizes` становится 100vw. Это меньше прежнего правила (200vw/170vw) на любом окне:
на iPhone и iPad со старой системой растяжение героя после правки растёт.

**Доказательство.**
- WebKit, коммит 36c5187, баг 305059 (10.01.2026) «Use CSS calc() parser in SizesAttributeParser
  rather than rolling a bespoke one». Удалённый `SizesCalcParser` принимал только `calc()`
  и `-webkit-calc()`. Тесты WPT `min(1px, 200vw)` и `max(-200vw, 1px)` в `parse-a-sizes-attribute-*`
  перешли из FAIL в PASS. В заметке WebKit «Features for Safari 26.4» сказано: «Safari 26.4 adds support
  for using the min(), max(), and clamp() math functions inside the sizes attribute».
- Отказ записи с неразобранной длиной — «continue» к следующей записи, а если не разобралась ни одна, —
  100vw (спецификация HTML и тот же WebKit). Опыт в Chromium: `foo(1px), 170vw` → 170vw; строка без
  разбираемых записей (`max(` заменено на `maxx(`) → ровно 100vw (390, 640, 800, 1000, 1024, 1440, 1920
  против прежних 780, 1280, 1600, 2000, 2048, 2448, 3264).
- Последствия на настоящих лестницах. Выбор кандидата — по модели Chromium; у WebKit детали выбора могут
  отличаться, но значение 100vw — факт. В скобках — растяжение, то есть нужная ширина в пикселях
  устройства, делённая на ширину кандидата.

  | страница, окно | до | после (Chromium) | после (Safari < 26.4) |
  |---|---|---|---|
  | `/max-payne-3/`, `/max-payne-2/` 390×844@3 | 1920 (×1,63) | 1920 (×1,63) | 1200 (×2,61) |
  | `/max-payne-1/` 390×844@3 | 2400 (×1,31) | 3200 (×0,98) | 1200 (×2,61) |
  | `/max-payne-3/` 430×932@3 | 1920 (×1,80) | 1920 (×1,80) | 1600 (×2,16) |
  | `/max-payne-3/` 375×667@2 | 1600 (×1,03) | 1920 (×0,86) | 1200 (×1,38) |
  | `/max-payne-1/` 820×1180@2 (iPad) | 3200 (×1,78) | 3200 (×1,78) | 2400 (×2,37) |
  | `/remake/` 390×844@3 | 1280 (×1,05) | 1280 (×1,05) | 1200 (×1,13) |

  На широких окнах с DPR 2 (1280–1512) выбор совпадает: 100vw × 2 всё равно выше верхнего кандидата.
- Таблица `rastyazhenie` и приёмка П93 п. 0г сняты только в Chromium, поэтому формально условие
  приёмки выполнено. Но довод «Как прочитано» п. 4 («чтобы это было свойством на любом окне…») неверен
  для этой доли браузеров.

**Что предлагаю** (правка только строки `sizes` маршрута, в пределах п. 0г). После каждой записи
с `max()` поставить запасную запись с тем же условием и прежним значением. Браузер, который не разобрал
`max()`, по правилу «continue» перейдёт к прежнему значению:
```
(max-width: 640px) max(200vw, …vh, …px), (max-width: 640px) 200vw,
(max-width: 1024px) max(200vw, clamp(…)), (max-width: 1024px) 200vw,
(min-width: 0px) max(170vw, clamp(…)), 170vw
```
Опыт в Chromium на 7 окнах (390×844 … 1920×1080):
- с разбором `max()` значения совпадают с нынешней строкой до пикселя (1046, 1280, 1859, 2000, 2141, 2509, 3264);
- без разбора (`max(` → `maxx(`) значения равны прежнему правилу (780, 1280, 1600, 2000, 2048, 2448, 3264).

`(min-width: 0px)` нужен затем, чтобы запись с `max()` не стояла без условия не последней: по спецификации
это ошибка разбора, хотя значение возвращается. Таблица `rastyazhenie` в Chromium от этого не меняется.
Комментарий уточнить: «не меньше "до" в любом браузере, который разбирает прежнее правило». Правка судьи —
снова «судью судят».

### P3-R1-MARSHRUT-2 | мнение

**Что не так.** Условия `(width <= 640px)` и `(width <= 1024px)` в `sizes` записаны синтаксисом сравнения
«как правила героя ниже». В CSS этот синтаксис закрывал щель 640–641 px между парой `max-width`/`min-width`.
В `sizes` такой щели нет: список читается до первого совпадения, и в нём только верхние границы.
Синтаксис ничего не даёт и сужает совместимость: Chrome < 104, Safari < 16.4.

**Доказательство.** Опыт в Chromium: условия испорчены (`(width <== …)`), то есть браузер без синтаксиса
сравнения, но с `max()`. Первые две записи отбрасываются, третья действует на всех ширинах.

| страница, окно | до | после |
|---|---|---|
| `/remake/` 640×900 | 1280 | 1088 |
| `/remake/` 800×600 | 1600 | 1360 |
| `/max-payne-3/` 1000×600 | 2000 | 1859 |
| `/max-payne-3/` 1024×600 | 2048 | 1859 |

Доля таких браузеров в 2026 году ничтожна, поэтому это мнение, а не дефект.

**Что предлагаю.** `max-width: 640px` и `max-width: 1024px` — те же включающие границы, что у ядра, и
понимают их все браузеры. Запасные записи из п. 1 тогда закрывают оба случая.

**Что не так.**

### P3-R1-MARSHRUT-6 | не подтверждено

**Что не так (гипотеза).** На мобильных браузерах с панелью адреса CSS `vh` (высота рамки `40vh`) считается
от большого окна. Значение `vh` внутри `sizes` может считаться от окна с видимой панелью. Тогда член

**Доказательство.** Опытом не проверено: у headless Chromium панели нет. Расчёт на нынешних лестницах:
390×844@3 даёт `sizes` × 3 ≈ 3138 (или около 2790 при малом окне), и выбор тот же — 1920 для
`mp2-art`/`mp3-art`, 3200 для `hero`. При DPR 2 — тоже без смены кандидата.

**Что предлагаю.** Ничего не править. Если появится лестница с шагом около 2800–3200, проверить на устройстве.

## Проверено — находок нет

- **Chromium разбирает строку целиком и точно.** Проверка лестницей кандидатов с шагом 1w от 50 до 9000:
  выбранная ширина равна расчёту, округлённому вверх, на 16 окнах, включая границы 640/641/1024/1025
  и низкие 640×300 и 1024×400. Примеры:

  | окно | расчёт | выбор |
  |---|---|---|
  | 390×844 | 1045,55 | 1046 |
  | 800×900 | 2508,39 | 2509 |
  | 1024×768 | 2140,49 | 2141 |
  | 1440×900 | 2508,39 | 2509 |
  | 1920×1080 | 3264 | 3264 |

  `vw`, `vh` и `px` внутри `max()`/`clamp()` смешиваются верно.
- **Монотонность выбора и «после ≥ до» в Chromium**, включая геометрическое среднее при DPR > 1. Окна:
  33 ширины от 320 до 2560 × 16 высот от 360 до 1440. Три лестницы: [1200, 1600, 1920], [1200, 1600, 2400, 3200],
  [1200, 1280]. DPR 1; 1,25; 1,5; 1,75; 2; 2,625; 3. Итог: **11 088 клеток, хуже 0, лучше 1159,
  неустойчивых 0**. Устойчивость проверена двойным замером прежней строки вокруг новой.
- **Границы диапазонов.** Ветвь `sizes` и ветвь раскладки ядра совпадают на 640/641 и 1024/1025:
  `(width <= 640px)` ≡ `(max-width: 640px)` по `matchMedia`, рамка на 641 — 641×809, на 1025 — 697×809.
  Дробную ширину окна опытом не получить: iframe шириной 640,5 округляется до 641. По устройству обе ветви —
  одно включающее условие на одной ширине окна.
- **Полоса прокрутки** (`vw` с полосой, рамка без неё) лишь завышает члены 200vw и 170vw. Члены с p от `vw`
  не зависят. Направление безопасное.
- **Рамка шире окна** (641–1024, `inset: 0 -20% 0 20%`): ширина рамки равна 100 % героя (замер: 800 на 800,
  641 на 641). Формула берёт именно её.
- **Пропорции кадров.** Атрибуты `width`/`height` на страницах совпадают с мастерами: `mp3-art` и `mp2-art` —
  1920×620, `hero` — 3840×1240, `mp1-k13` — 1280×960. Коэффициенты округлены вверх верно:

  | p | до 640 | 641 и шире |
  |---|---|---|
  | 3,0968 | 123.88vh, 805.17px | 1858.07px, 278.71vh, 2849.04px |
  | 1,3333 | 53.34vh, 346.67px | 800px, 120vh, 1226.67px |

  Округление высот кандидатов (3200×1033 даёт пропорцию 3,0978 против 3,0968) — 0,03 %, пренебрежимо.
  На `/remake/` новые члены почти никогда не больше прежних, и правка там практически ничего не меняет.
- **Двойной загрузки нет.** В своём контексте, с подменой HTML на прежнюю строку `sizes` через `route`:
  по одному запросу кадра героя на загрузку и у прежней, и у новой строки (3 страницы × 4 окна/DPR).
  Двойные запросы одного адреса в первом замере — артефакт `setViewportSize` в переиспользуемом контексте:
  со свежим контекстом их нет.
- **Прочие страницы.** `sizesGeroya` вызывается только в ветви героя. Страницы без героя и главная
  (`HomeHero.astro` с прежним правилом) не затронуты.
- **`astro check`** не запускался: запрещено, пишет в `.astro/` сайта. По чтению препятствий нет. Тип
  параметра `{ width: number; height: number }` принимает `ImageMetadata` (`Kadr.src` необязательным
  не объявлен). Вложенного шаблона внутри `${…}`, ловушки сканера фронтматтера (строки 253–255), нет.
- **Firefox — по знанию, опытом не проверено.** Длина `sizes` разбирается общим разборщиком длин Servo
  с математическими функциями (с Firefox 75). Синтаксис сравнения есть с Firefox 63. Разбор строки
  ожидается верным.

### P3-R1-INSTR-2 | дефект шапки (обещает больше, чем делает) | `zanizhenie.js`: самопроверка «разбор совпал с браузером» проверяет только корзину кандидата; довод «браузер своего значения не отдаёт» неверен

**Что не так.** Шапка (строки 12–15): «разбор sizes — свой, не браузера (браузер своего значения не
отдаёт); проверка — … выбранный кандидат обязан быть наименьшим из тех, что не меньше значения …
— это сверяет, что разбор совпал с браузером». На деле:
1. Проверка подтверждает только, что значение лежит в промежутке (предыдущий кандидат; выбранный].

   px, кроме низких) — там «ждали» = наибольший при любом значении, и проверка ничего не проверяет.

   а число занижения печатается с точностью 0,001.
2. Браузер своё значение отдаёт: при srcset с `w` `img.naturalWidth` = ширина файла × sizes / w;

героя `/max-payne-3/` и заданным sizes, разбор — дословно логикой `zanizhenie.js`:

```

(width <= 640px) 100vw, 1500px → разбор [— | 1500px] = 1500; браузер (naturalWidth) 1499; кандидат 1600, ждал 1600 — СОВПАЛО
```

Четыре неверных разбора из пяти — «несовпадений 0».

**Доказательство 2 — на настоящих данных разбор верен (вывод итога держится).** 27 клеток
(`/max-payne-3/`, `/max-payne-1/`, `/remake/` × 1060x600, 1100x600, 1025x600, 641x900, 1440x900,

srcset) равна его дескриптору во всех 27 (1200/1600/1920/2400/3200/1280).

**Что предлагаю.** Самопроверку заменить или дополнить сверкой `|разбор − naturalWidth × w /

не меняется — числа подтверждены независимо.
