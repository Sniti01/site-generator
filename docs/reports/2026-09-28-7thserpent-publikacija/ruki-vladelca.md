## Подготовка — домен не трогается

### 1. Вливание ветки сессии в `main`

После вашей приёмки глазами — ваше слово «вливай» (или вливаете сами). Без этого кнопки запуска нет: GitHub
даёт Run workflow только файлу, который лежит в `main` (урок первого сайта, доклад 2026-09-15, «Факты» п. 9).

**Проверка:** Actions → слева есть **Deploy 7thserpent.com**. Push этого вливания запустит workflow, и он
закончится **skipped** — переменной `SERPENT_DEPLOY` ещё нет, так и задумано.

### 2. Приватный репозиторий корпуса и ключ только для чтения

Сторож 8 слов собирается только с сырым корпусом (612 файлов `.gz`, 59,4 МБ; в публичный репозиторий он не идёт).

1. GitHub → **New repository**: владелец `Sniti01`, имя **`7thserpent-corpus`** — буква в букву (оно записано
   в workflow), **Private**, без README.
2. На своём компьютере — копия сырья в отдельную папку и первый коммит (Git Bash):
   ```
   cp -r /d/SEO/cloud/site-generator/sites/7thserpent.com/input/corpus/raw /d/SEO/cloud/7thserpent-corpus
   cd /d/SEO/cloud/7thserpent-corpus
   git init -b main
   echo "* -text" > .gitattributes
   git add -A
   git commit -m "Корпус 7thserpent.com: input/corpus/raw как есть"
   git remote add origin https://github.com/Sniti01/7thserpent-corpus.git
   git push -u origin main
   ```
   Корень репозитория — сами папки хостов (`acclaimmag.com/`, `almarsguides.com/`, …), **без** папки `raw` сверху.
3. Ключ развёртывания: `ssh-keygen -t ed25519 -f 7thserpent-corpus-key -N "" -C "deploy 7thserpent corpus"` —
   получится пара файлов. В репозитории **7thserpent-corpus** → Settings → **Deploy keys** → Add deploy key:
   Title — `site-generator CI`, Key — содержимое `7thserpent-corpus-key.pub`, **Allow write access — выключено**.
4. Закрытую половину (`7thserpent-corpus-key`, без `.pub`) — в секрет `SERPENT_CORPUS_KEY` репозитория
   **site-generator** (шаг 4). После этого оба файла ключа удалить с компьютера.

**Проверка:** в 7thserpent-corpus на главной странице репозитория — 241 папка хостов и `.gitattributes`;
в Deploy keys — одна строка с пометкой **Read-only**.

### 3. Сайт в панели и робот FTP

*Экран: панель «Хостінг Україна».* До этого шага домен хостером не отвечает: запись Cloudflare на хостер
не ведёт — и не поведёт до шага 8.

1. **Хостинг → Мої сайти → додати сайт** `7thserpent.com`, кореневий каталог — **`7thserpent.com/www`**.
2. **Хостинг → Файли → FTP** («Користувачі FTP») → новый пользователь-робот **только для второго сайта**
   (не робот первого сайта: сторож откажет, если логин совпадёт с `AC4BF_FTP_USER`). **«Каталог доступу»** —
   **`7thserpent.com/www`**; «Тільки читання» — выключено.
3. Файловый менеджер панели → `7thserpent.com/www`: **если хостер положил туда свою заглушку (`index.html`
   или другие файлы) — удалить**, папка должна быть пустой (допустимы только служебные папки `.well-known/`
   и `cgi-bin/`). Иначе сторож откажет: заглушка не наша (у неё нет `canonical` https://www.7thserpent.com/),
   а непустой каталог без нашей сборки сторож папки не пропускает — `mirror --delete` стёр бы его.

**Проверка:** в списке пользователей FTP — строка робота с каталогом `7thserpent.com/www`; папка `www` пустая.
По желанию — FileZilla этим логином (явный FTP через TLS, порт 21): пустая папка, **не** папки сайтов
и **не** папка `www`.

### 4. Секреты GitHub

*Экран: https://github.com/Sniti01/site-generator/settings/secrets/actions → вкладка **Secrets** → New repository secret.*

| Name — буква в букву | Что вставить |
|---|---|
| `SERPENT_FTP_HOST` | хост FTP из строки доступа робота в панели (между `@` и `:`) |
| `SERPENT_FTP_PORT` | `21` |
| `SERPENT_FTP_USER` | логин робота второго сайта (до `@`) |
| `SERPENT_FTP_PASSWORD` | его пароль — только здесь |
| `SERPENT_CORPUS_KEY` | содержимое файла `7thserpent-corpus-key` целиком, со строками `-----BEGIN…` и `-----END…` |

`AC4BF_FTP_USER` у первого сайта уже есть — workflow читает его только для сверки «робот не тот же»
и не печатает. **Во вкладку Variables секреты не класть.** `SERPENT_DEPLOY` и `SERPENT_LIVE` сейчас
**не заводить** (шаг 10).

**Проверка:** в списке Secrets — пять новых имён рядом с четырьмя `AC4BF_FTP_*`.

### 5. Первая выкладка — вручную, домен не привязан

Actions → **Deploy 7thserpent.com** → **Run workflow** → ветка `main`, **SERPENT_FIRST = `on`** → Run.

Что сделает робот: проверит секреты, заберёт корпус, соберёт сайт со всеми гейтами и сторожами, проверит свою
папку, `index.html` и то, что лежит внутри папок, решит, первая ли это выкладка (вход `on` — или на сервере нет
нашего `index.html`: такой запуск первый и со входом по умолчанию), спросит домен (ждёт «не привязан»), сверит
сборку CI со сборкой, принятой в сессии 22 (165 файлов, sha256 — после нормализации значений `data-astro-cid`
компонентов ядра и хешей имён CSS: их Astro считает от пути ядра на машине, на раннере он другой), выложит файлы —
главную последней — и пересчитает их на сервере. Домен по-прежнему ничего не покажет. Если выкладка оборвётся,
главной на сервере не будет, и повторный запуск снова считается первым — со сверкой сборки.

**Проверка:** зелёная галочка; в журнале — «папка робота: пустой корень», «глубина: внутри папок сайта чужого
нет», «первая выкладка: да», «домен не привязан», «сборка CI = принятая (816ba46): 165 файлов, sha256 те же;
побайтно иных N — только значения data-astro-cid…», «на сервере ровно dist/: 165 файлов». **Красный крест** — робот остановился до сервера или
сказал почему; пришлите мне строку `СТОП` из журнала (репозиторий публичный, журнал я читаю сам). Если красная
«сборка CI не равна принятой» — сервер не тронут, в журнале — список сборки CI для разбора: это разница сборки
Linux и Windows, которую нормализация не покрывает (картинки `sharp`, иконки гейта знака, версия Node); решаем
вместе. Если сборка упала раньше, на гейте знака, — та же причина (иконки перерисовываются через `sharp`).

1. В панели — почтовый ящик на домене `7thserpent.com` (адрес выбираете вы).

## Cloudflare и сертификат — до привязки

### 7. Настройки зоны `7thserpent.com`

| Где в Cloudflare | Что | Почему |
|---|---|---|
| Scrape Shield → **Email Address Obfuscation** | **Off** | иначе адрес на `/privacy/` превращается в `__cf_email__` со скриптом (так было у первого сайта, П77 п. 6) |
| SSL/TLS → Edge Certificates → **Always Use HTTPS** | **Off** | край сделает второй скачок `http://` → `https://` → `www`; проверка «одним скачком» покраснеет (П54, дополнение) |
| Security → Bots (AI Crawl Control) → **управляемый robots.txt** | **выключен** | Cloudflare приписывает к нашему `robots.txt` свой блок, закрывающий ИИ-роботов; наш файл их не закрывает. У первого сайта блок исчез только после отключения старой настройки `is_robots_txt_managed` (доклад 2026-09-15, раздел 6) |
| SSL/TLS → Overview | **Full (strict)** — после сертификата в панели | шифрование и до хостера, с проверкой сертификата |

Сертификат **Let's Encrypt в панели** хостера для `7thserpent.com` и `www.7thserpent.com` — **до** того, как
запись Cloudflare поведёт на хостер: `.htaccess` сразу ведёт на `https`, без сертификата сайт не откроется.
Если панель выпускает сертификат только при записи, уже ведущей на хостер, — выпустить его сразу после шага 8,
в ту же минуту, и только потом Full (strict).

**Проверка:** четыре переключателя — как в таблице; в панели сертификат «активний» для обоих имён.
Строки `npm run live:check` (шаг 9) это же и проверят: «блока Cloudflare нет», «без обфускации почты»,
три редиректа одним скачком.

## Проверка https

### 9. `live:check`

Скажите мне «домен привязан» — я соберу сайт из выложенного коммита `main` (проверка сверяет HTML каждой страницы
со сборкой `dist/`) и запущу `npm run live:check -w sites/7thserpent.com` (44 проверки: редиректы с путём,
главная, `robots.txt` мимо кэша и тот, что берут роботы, карта и все её адреса, 404, `/privacy/` с адресом ящика,
HTML страниц = сборка, кэш Cloudflare у страниц, `X-Robots-Tag`, cookies). Ждём **44/44**; строка «адрес ящика
открытым текстом» зелёная только после захода «ящик заведён» (шаг 6). Если красная строка `Set-Cookie` или
«вставки Cloudflare» — в строке названы имя cookie или вставка: решаем, что выключить в Cloudflare (Bot Fight
Mode, Web Analytics) или что писать на `/privacy/` (страница обещает: cookies нет, сторонних запросов нет).
Красная «обход кэша сработал» или «наш файл целиком» со словами «ответ из кэша Cloudflare» — очистить кэш
`robots.txt` в Cloudflare (Caching → Purge by URL) и повторить.

### 10. Переменные выкладки — только после зелёного шага 9

Settings → Secrets and variables → Actions → вкладка **Variables** → New repository variable:
**`SERPENT_DEPLOY` = `on`** (выкладка по push в `main`), **`SERPENT_LIVE` = `on`** (live:check после каждой
выкладки).

**Проверка:** две переменные в списке Variables; следующий push в `main` по файлам сайта — прогон со строкой
«домен отвечает: выкладка обновит живой сайт» и зелёным live:check.

Позже, если сайт уберёт файл первого уровня (например, старую картинку в корне), выкладка остановится со строкой
«рядом с нашей сборкой записи, которых нет ни в этой сборке, ни в карте сайта прежней выкладки (… имя …)»: сервер
не тронут; если имя — наш старый файл, удалите его в файловом менеджере панели и запустите выкладку снова.
Убранные страницы сторож узнаёт сам — по карте сайта прежней выкладки.

### 11. Кеш статики в панели

Статику (CSS, шрифты, картинки, иконки) у этого хостера отдаёт nginx, а не Apache: `.htaccess` на неё
не действует, поэтому правил статики в нём нет (бэклог 60 п. 11). В панели — правило кеша:

- `/_astro/*` — долгий кеш (год): в именах этих файлов хеш содержимого, правка меняет имя;
- **иконки без хеша в имени** — `/favicon.ico`, `/favicon.svg`, `/favicon-16x16.png`, `/favicon-32x32.png`,
  `/icon-192.png`, `/apple-touch-icon.png` — **короткий** кеш (день или меньше): иначе правка знака дойдёт
  до вернувшихся читателей через год.

**Проверка:** в браузере — DevTools → Network → `favicon.svg` → заголовок `Cache-Control` без `max-age=31536000`.
