## Часть A. Шесть развилок §7B

### Развилка 1 — источник истины о страницах

**Варианты:** (а) структура — единственный источник, страниц вне неё не
существует, билд падает на странице вне структуры (прецедент 7dtd, 87 стр.);
(б) папки контента главные, структура валидирует (прецедент 1weekinvr).

**Рекомендация: (а).** Фабрика собирает сайт из данных брифа и семантики —
файловая раскладка контента есть удобство, а не истина. У 7dtd это проверено
боем: `getPage()` бросает исключение, маршрут строится из поля `url`
фронтматтера, а не из пути файла. Вариант (б) на 1weekinvr уже показал цену:
`type` из 14 свободных значений не читает ни один скрипт.

### Развилка 2 — `parent` или `level`

**Варианты:** (а) `parent: url` (7dtd); (б) `level: int` (1weekinvr).

**Рекомендация: (а).** Крошки, дерево, поиск сирот и `BreadcrumbList`
считаются одним обходом; `level` выводится из `parent`, обратное — нет.
Глубина ограничивается валидатором (`MAX_DEPTH = 2`, из брифа).

### Развилка 3 — дублируются ли SEO-поля

**Варианты:** (а) `title / h1 / description / keywords / parent / related`
живут только в структуре, контент-файл связан одним полем `url` (7dtd);
(б) дублируются во фронтматтере.

**Рекомендация: (а).** Дубль — это два источника, которые разойдутся;
у 7dtd связка одним полем проверена. Уникальность `title/description/h1`
по всему сайту — обязанность валидатора.

### Развилка 4 — тип→блоки: данными

**Варианты:** (а) `blocks[]` — поле страницы в структуре, со словарём
умолчаний «тип → блоки» в данных ядра; (б) как у 7dtd — текстом брифа
в скрипте; (в) не формализовать.

**Рекомендация: (а).** Это уже предрешено записями: пункт 1 бэклога требует,
чтобы выход анализа конкурентов писался в `blocks[]` с источником и
уверенностью; REUSE §3 доказал на 1weekinvr, что `type` без `blocks[]`
декоративен. Формат элемента — в Части B.

### Развилка 5 — поиск

**Варианты:** (а) волна 1 без поиска; pagefind + UI-компонент — волной 2,
в ядро только вместе; (б) подключать сейчас.

**Рекомендация: (а).** 30 страниц ходятся навигацией и картой сайта; у 7dtd
pagefind собран (1,6 МБ) и мёртв без UI — записан в костыли. Проверить факт:
если в шапке осталась форма поиска, ведущая в никуда, — скрыть до подключения,
битый вход хуже отсутствия.

### Развилка 6 — журнал решений и `unresolved`

**Варианты:** (а) единый корневой `DECISIONS.md` (посайтовое — с пометкой
сайта) + завести `docs/UNRESOLVED.md` по жанру 7dtd; статус страницы — полем
в структуре (`status`, `wave`), отдельный csv не заводить; (б) посайтовые
журналы.

**Рекомендация: (а).** Один журнал уже работает и держит 22 решения; второй
рядом — тот тип дублирования, который сам же REUSE занёс в костыли. Жанр
`unresolved` («чего не удалось установить — строкой сюда, а не тихой
заглушкой») переносится как есть: анатомический проход по корпусу будет
давать неопознанное регулярно.

## Часть B. Контракт structure.json — рамка

Схему пишет Code по прецедентам §5 REUSE; рамка полей страницы:

```
url, type, h1, title, description, cluster, keywords[], parent,
related[], blocks[], wave (1|2), status (planned|draft|published),
owner (true — страница владельца, живёт вне частотного порога)
```

Плюс два реестра с причиной у каждой строки: `exclusions[]` (не по теме)
и `no_page[]` (по теме, страницу не делаем). Правило учёта — из 7dtd,
дословно: **каждый запрос ровно один раз** — страница, exclusions или
no_page; иначе валидатор падает. `keywords` сверяются с исходной выгрузкой
посимвольно.

Элемент `blocks[]`:

```
{ "block": "kebab-имя", "role": "контентная роль (опц.)",
  "source": "manual | anatomy | type-default",
  "confidence": "high | medium | low",
  "evidence": "7/9 (только для anatomy)" }
```

Границу не смешивать (пункт 1 бэклога): анатомия конкурентов задаёт
SEO-пол (что обязано быть), референсы и DESIGN — вид. `blocks[]` несёт пол.

## Часть C. Правила судеб кластеров

Не 258 решений по одному, а правила; владелец подтверждает пачки, не строки.

1. **Бренд-голова.** Кластер `assassins` (139 тыс.) — главная. Брендовые
   кластеры игр — хабы своих игр/эпох.
2. **Магазинный интент → `no_page`.** Признаки (любой): `% Агрегаторов`
   выше порога; в топе снимка ≥5 из 10 — маркетплейсы и сторы (allegro,
   ceneo, mediaexpert, консольные магазины); недобор корпуса по отказам
   магазинов. У каждой записи — причина.
3. **Платформенные кластеры** (`<игра> xbox/ps4/ps5/switch/pc/steam`) —
   по умолчанию сливаются ключами в хаб игры (раздел «Na czym zagrać»);
   отдельная страница только при информационной выдаче и заметном объёме.
4. **Хвост.** Пороги по Google-сумме кластера: ниже нижнего — слияние
   в родителя или `no_page`; средняя зона — волна 2 или слияние по смыслу;
   выше — кандидат в страницы. Числа порогов Code выводит из фактического
   распределения (гистограммой) и предлагает; пороги — данные, не хардкод.
5. **«Некластеризовано» (264 фразы).** Code раскладывает каждую: к кластеру /
   новая тема / exclusions / no_page, с уверенностью; владелец подтверждает
   пачками. Чужие вселенные (witcher и т.п.) — exclusions.
6. **Антиканнибализация.** Один кластер = одна страница; детектор пересечения
   топов ≥50 % — из 1weekinvr.

## Часть D. Волна 1 — критерий отбора 30

1. **Волна — связное дерево, не топ-30 списком:** родитель каждой страницы
   волны сам в волне.
2. **Обязательные места:** главная; хабы игр с существенной Google-суммой;
   `/poradniki/od-czego-zaczac/` — на неё указывает единственный CTA главной,
   битых входов в волне быть не может; карта исторических мест (страница
   владельца, `owner: true`, вне порога).
3. **Добор до 30** — по Google-сумме кластера, при прочих равных предпочтение
   корзине покрытия high (анатомия с порогом частоты). Страницы low-корзины
   допускаются с пометкой: `blocks[]` без анатомии, только план содержания.
4. Карта: одна страница или хаб с подстраницами мест — решается по факту
   разбора «Некластеризовано» и корпуса; на старте — одна страница,
   расширение волной 2.
