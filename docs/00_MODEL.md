# Site Factory — модель проекта

> Это не «сайт». Это конвейер: из брифа (структура + референсы + ТЗ) собирается готовый
> многостраничный сайт с собственной дизайн-системой. Каждый следующий сайт должен
> собираться быстрее предыдущего за счёт накопленного ядра.

---

## 1. Три слоя, которые нельзя смешивать

| Слой | Отвечает за | Источник данных | Артефакт |
|---|---|---|---|
| **Структура** | какие страницы существуют, их типы, URL, ключи | бриф / кластеризация / SEO Pipeline | `structure.json` |
| **Дизайн** | как это выглядит: токены, сетка, блоки | референсы + скилл `impeccable` | `DESIGN.md` + компоненты |
| **Контент** | как текст ложится в блоки | бриф / готовые тексты SEO Pipeline | `content/*.md` + маппинг |

Имя `DESIGN.md` — не наше решение, а канон скилла `impeccable`: оно захардкожено
в `DESIGN_NAMES`, на него завязаны загрузка контекста, сайдкар `.impeccable/design.json`
и проверка дрейфа в `doctor`. Переименовывать нельзя. Файл посайтовый и лежит
в `sites/<домен>/`, тогда как `PRODUCT.md` — фабричного уровня и наследуется от корня.

Ошибка, которой надо избежать: дизайн, придуманный до того, как известна структура,
и текст, залитый в дизайн, который под него не рассчитан. Порядок всегда:
**структура → карта блоков → дизайн → контент в блоки.**

## 2. Вход: единый бриф

Один файл на проект — `brief/site.yaml` (шаблон в `01_BRIEF_TEMPLATE.yaml`).
Всё, что нужно для запуска, лежит там. Ничего не передаётся «на словах в чате».

### 2.1. Источник структуры — три варианта

| `structure.source` | Что подаётся на вход | Статус |
|---|---|---|
| `landing` | одна страница, список блоков и смыслов | готово |
| `clusters` | файл семантики, разбитой на группы (кластеры) | готово |
| `seo-pipeline` | структура + **готовые тексты** из проекта SEO Pipeline | ждёт конвертер |

Для `seo-pipeline` сейчас закладывается **адаптер с фиксированным контрактом**: конвейер
не знает, откуда взялся файл, он знает только формат `structure.json`. Пока конвертер
не готов — адаптер читает ручной экспорт того же формата. Когда конвертер будет
готов, меняется только адаптер, конвейер не трогаем.

### 2.2. Референсы — два уровня

1. **Глобальные** — сайт целиком: URL + *что именно нравится* (обязательно словами:
   «воздух между блоками», «типографика заголовков», «тёмная тема с акцентом»).
   Без расшифровки референс бесполезен — копируется случайное.
2. **Поблочные** — «блок бонусов вот здесь выглядит так, сделай подобное».
   Каждый поблочный референс привязан к **типу страницы** и **имени блока**.

Референс не копируется пиксель-в-пиксель. Из него извлекается *принцип*
(ритм, плотность, контраст, иерархия) и переносится на свою типографику и палитру.

### 2.3. Типы страниц и блоки

Пользователь указывает типы страниц в брифе. Если тип не указан, но в структуре
он явно есть — конвейер его достраивает сам и **пишет об этом в `DECISIONS.md`**.

## 3. Три режима работы

| Режим | Поведение | Когда |
|---|---|---|
| `normal` | задаёт **до 5** уточняющих вопросов пачкой, потом работает без остановок | по умолчанию |
| `auto` | не спрашивает ничего, пробелы закрывает сам, все допущения пишет в `DECISIONS.md` | поток, много сайтов |
| `interview` | ведёт по всем разделам брифа вопрос за вопросом, сам предлагает варианты | вводных почти нет |

Общее правило для всех режимов: **вопросы задаются один раз, до начала сборки.**
Не «сделал блок — спросил — сделал блок». В `auto` каждое самостоятельное решение
фиксируется строкой в `DECISIONS.md`, чтобы правки были точечными, а не «переделай всё».

## 4. Конвейер: 7 стадий

```
0. RECON      → разбор существующей базы и старых сайтов          (один раз на весь проект)
1. INTAKE     → бриф → structure.json (нормализация)
2. REFERENCE  → разбор референсов → направление дизайна
3. BLOCKMAP   → тип страницы → последовательность блоков
4. CONTENT    → раскладка текстов по блокам (если тексты есть)
5. BUILD      → impeccable: дизайн-система → компоненты → страницы
6. QA         → SEO + визуальная проверка + отчёт
```

**0. RECON** — выполняется один раз при создании фабрики: разбираются текущий макет
главной, `1weekinvr.com` и `7dtd.com.pl`; всё пригодное вытаскивается в ядро.

**1. INTAKE** — любой из трёх источников приводится к одному `structure.json`:
```
pages[]: { url, type, h1, title, description, cluster, keys[], parent, text_ref }
```

**2. REFERENCE** — по каждому референсу пишется 3–5 строк: что взято, что не взято.
Результат — направление: палитра, типографическая пара, плотность, сетка, характер
анимации.

**3. BLOCKMAP** — для каждого типа страницы фиксируется последовательность блоков и
**правила вариативности**: внутри одного типа страницы не должны выглядеть одинаково
(порядок блоков, чередование вариантов, разные акценты).

**4. CONTENT** — ключевая стадия для `seo-pipeline` (см. §6).

**5. BUILD** — подключается скилл `impeccable`, собирается дизайн-система, потом
компоненты блоков, потом шаблоны типов страниц, потом генерация всех страниц.

**6. QA** — чек-лист в `02_CLAUDE_CODE_TASK.md`.

## 5. Реестр типов страниц

Базовый набор, из которого собирается любой сайт:

- `home` — главная
- `hub` — категория / раздел кластера
- `entity` — карточка сущности (товар, игра, оффер, инструмент)
- `article` — статья / гайд
- `listing` — подборка, топ, рейтинг
- `comparison` — сравнение
- `faq` — вопросы-ответы
- `info` — служебные (о нас, контакты, правовые)

Тип = набор блоков + правила SEO (шаблон title/description, разметка, перелинковка).

---

## 6. Готовые тексты из SEO Pipeline: главное требование

Готовый SEO-текст **нельзя вываливать полотном**. Правило раскладки:

1. Текст режется по смысловым узлам (обычно по H2) — каждый узел получает свой блок.
2. Блоки чередуются по типу подачи: текст → список/карточки → цифра/акцент →
   таблица → цитата/вывод → текст. Два одинаковых блока подряд запрещены.
3. Из текста вытаскиваются **опорные факты** (числа, шаги, сравнения) и выносятся
   в визуальные элементы, а не остаются в абзаце.
4. Длинные разделы получают якорное оглавление.
5. У страницы должна читаться драматургия: заход → польза → доказательство → действие.
   Не «SEO-партнёрка», а материал, который дочитывают.
6. **Текст не переписывается** без разрешения — он оптимизирован под запросы.
   Разрешено: резать на блоки, добавлять подзаголовки-микрокопию, выносить списки.
   Любое изменение самого текста — в `DECISIONS.md`.

Ограничение по плотности: непрерывный текстовый блок — не длиннее ~900 знаков,
дальше обязателен визуальный разрыв.

## 7. Репозиторий: ядро + темы

```
site-generator/            ← workspace root: { "workspaces": ["sites/*"] }
├─ core/                  ← общее, растёт от проекта к проекту
│  ├─ blocks/             ← библиотека блоков (варианты, контракты данных)
│  ├─ layouts/            ← шаблоны типов страниц
│  ├─ seo/                ← мета, schema.org, sitemap, перелинковка
│  └─ adapters/           ← clusters / seo-pipeline → structure.json
├─ .claude/skills/        ← impeccable + свои команды конвейера
├─ docs/                  ← эта модель, чек-листы, REUSE.md
├─ PRODUCT.md             ← фабричного уровня, наследуется всеми сайтами
├─ DECISIONS.md
└─ sites/
   ├─ _template/
   ├─ ac4bf-thewatch.com/ ← первый сайт; переехал, см. его MIGRATION.md
   └─ <site-name>/        ← бриф, тема, structure.json, контент, DESIGN.md, оверрайды
```

Принцип: сайт **не форкает** ядро. Сайт = бриф + тема + оверрайды. Улучшение,
сделанное на одном сайте и пригодное всем, переносится в `core/` отдельным шагом.

Две детали раскладки, которые выглядят косметикой, но таковой не являются:
скиллы лежат в `.claude/skills/`, потому что Claude Code читает только оттуда;
папка сайта — одновременно корень Astro-приложения и `projectRoot` для
`impeccable`, и это единственная раскладка, при которой у каждого сайта свои
`.impeccable/` и `DESIGN.md`, а брифы поверхностей не осиротеют.

### 7.1. Ядро извлекается из первого сайта, а не наоборот

Главная `ac4bf-thewatch.com` сделана раньше, чем появилось ядро. Поэтому направление
переноса такое: сайт живёт и работает, из него **по одному** вынимаются блоки в `core/`,
и после каждого выноса главная проверяется на идентичность. Не «перепишем главную под
ядро» — так теряются наработки, ради которых всё и затевалось.

---

## 8. Что накапливается

После каждого сайта в ядро возвращается: новые блоки, новые варианты существующих
блоков, уточнения SEO-шаблонов, разобранные референсы. Через 3–4 сайта сборка
нового должна сводиться к «бриф + тема + правки».
