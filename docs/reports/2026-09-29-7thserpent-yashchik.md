## 5. Вход «домен привязан» — «судью судят»

**Что сделано.** Вход `SERPENT_DOMAIN_BOUND`: выбор `off`/`on`, по умолчанию `off`, в описании — имя входа и «после
красного прогона — новый Run workflow». Workflow передаёт его только шагу «Домен уже привязан?» и только в первой попытке
запуска:

```yaml
SERPENT_DOMAIN_BOUND: ${{ github.run_attempt == 1 && inputs.SERPENT_DOMAIN_BOUND || 'off' }}
```

Push — всегда `off`. Сторож домена при первой выкладке со входом `on` печатает по каждому имени, что отвечает: состояние,
причину, `<title>`, путь. Выкладка идёт, **если оба имени отвечают с этого хоста**: вся цепочка — по именам сайта,
конечный ответ — с имени сайта, чужого `canonical` нет. Иначе — стоп и со входом, своей причиной:
- ошибка TLS или сертификата — «выпусти Let's Encrypt в панели»;
- сеть или таймаут — «новый запуск кнопкой Run workflow»;
- одно имя не привязано;
- петля — «переадресация между www и голым именем в панели спорит с `.htaccess`»;
- «домен ведёт не на этот сайт».

Без входа — стоп, как до сессии; вход предлагается, только когда он поможет. Строки в публичный журнал очищены: без
невидимых знаков, `##[` и `::` погашены, куски ответа обрезаны. Сопоставители проблем `setup-node` сняты до печати.
Прочие сторожа — ни строки логики. Шапка workflow — без Cloudflare.

## 9. Факты, важные будущим сессиям

1. **Сторож домена со входом пропускает только домен, который отвечает по обоим именам с этого хоста.** Если первая
   выкладка остановится на домене, в строке `СТОП` названа причина.
2. **Вход работает только в первой попытке запуска** (`github.run_attempt == 1`). Повтор — новым Run workflow; так же
   сказано в описании поля и в листе.
3. **Правка сайта до первой выкладки — новый список принятой сборки:** `node tools/storozha-vykladki.mjs spisok dist
   <коммит> > gates/sborka-prinyataya.json` из папки сайта.
4. **`check-live` без кэша Cloudflare строг к `robots.txt`:** любая разница ответов с параметром и без — ПЛОХО (пределы
   CL23-Z-1, Z-2). В сессии 24 снять живой `robots.txt` двумя парами запросов — прежде чем решать, смягчать ли проверку.
5. **Инструмент правки и записи превращает экраны вида «обратная косая, u, код» (для U+202E, U+2028) в сами знаки.** В исходнике невидимые знаки — только из кодов
   (`String.fromCharCode`); после правок — сканер сырых знаков. В сессии это дважды испортило пробы: раз — синтаксис,
   раз — сырые двунаправленные знаки.
6. **Скептикам нужна копия вне репозитория или чтение на месте.** Пробы сторожей тянут ядро через `@factory/core`, копия
   без переходов не соберётся, а переходы в scratchpad опасны при удалении (`Remove-Item -Recurse`). В этой сессии
   скептики сторожа читали пробы на месте, а я не трогал их предмет.
7. Ключи TLS из проб скептиков в доклад не берутся (`tls/` раунда 2 пропущен при копировании).
8. `proverki` — около 4 минут, 2029 проб.

## 10. Открытые вопросы

### Технические — решены

1. **`check-live`, проверка 11 — по четырём заголовкам-следам.** `cf-ray`, `server: cloudflare`, `cf-cache-status`,
   `cf-mitigated`. Любой у любого ответа — ПЛОХО. Регистр имени заголовка не важен (`Headers.get`).
2. **Порчи возможностей Cloudflare — на образце с Cloudflare.** Без кэша на пути порча `robots.txt` на сервере — в обоих
   запросах (`oba`).
3. **Смягчение проверки 4 не делалось** (CL23-Z-1, Z-2). Это правка логики, а П108 велит «прочее не трогать». Пределы —
   тестами `todo`; решение — по живому образцу (П107 п. 6).
4. **Вход — только в первой попытке запуска** (SV23-O-6). Альтернатива — пускать согласие в повтор, если на сервере нет
   нашей выкладки. Отклонена: она ослабила бы защиту от отката.
5. **Переадресация самой страницей не судится** (SV23-O2-1). Белый список форм ответа дал бы ложный стоп, пока пустой
   `www` хостера не измерен.
6. **Подсказки прочих сторожей не правились** (SV23-O2-8, «остальные сторожа не меняются»). Сторож домена и лист ведут
   к новому Run workflow.
7. **Порядок «сначала падающие пробы» в раунде 2 восстановлен через `git stash`.** Первый красный прогон упал на
   синтаксисе проб. Правку сторожа я внёс раньше настоящего красного прогона, поэтому отложил её, прогнал пробы на `9ca1aa2`
   (упало 11 из 141), закоммитил пробы и вернул правку.
8. **Два моих образца в пробах раунда 2 были неверны**, это не ошибки сторожа. `[::1:bad]` — законный IPv6; скобка после
   «не Re-run» в регулярке требовала больше, чем обещает подсказка. Поправлены до зелёного прогона.

### Политические — для вас

**Вопрос 1. Согласие «домен привязан» уже, чем моя запись «Как прочитано» П108 п. 6.** Там я записал: со входом сторож не
останавливает «ни при «отвечает», ни при «не понять»». Суды показали: при таком прочтении первая выкладка уходит на
домен с битым сертификатом (`.htaccess` поведёт всех на https с ошибкой), на неразрешимое `www` или на чужой хост.

| Вариант | Что это | Цена |
|---|---|---|
| **(А) Как сделано** (рекомендую) | согласие — только при ответе обоих имён с этого хоста; иначе стоп и со входом, с причиной | вход не «проходит всегда»; при сбое — новый запуск после правки в панели |
| (Б) Буква ваших слов | со входом — проход при любом ответе и при ошибке, строка ответа в журнале | первая выкладка может сделать сайт недоступным (сертификат) или лечь мимо домена |

Сегодня домен отвечает заглушкой по обоим именам с сертификатом — по листу выкладка проходит при обоих вариантах.

**Вопрос 2. Повтор (Re-run) любого старого запуска выкладки откатывает живой сайт** (бэклог 72 п. 4). Сессия 23 закрыла
это для запуска первой выкладки. Повтор старого push-запуска или ручного не первого запуска выложит сборку своего коммита
поверх новой, без стопа. Так было и до сессии 23.

| Вариант | Что это |
|---|---|
| (А) Оставить | повтор — осознанный откат |
| **(Б) Сторож «коммит запуска = голова `main`»** (рекомендую) | в отдельной сессии после запуска — вместе с переносом сторожей в первый сайт (П107 п. 5); откат — отдельным входом |

Рекомендация — **(Б) после запуска**. До запуска повторять нечего.
