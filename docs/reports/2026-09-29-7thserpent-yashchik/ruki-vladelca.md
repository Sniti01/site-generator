### 1. Вливание ветки сессии в `main`

После вашей приёмки глазами — ваше слово «вливай» (или вливаете сами). Push вливания запустит workflow, и он закончится
**skipped** — переменной `SERPENT_DEPLOY` нет, так и задумано.

**Проверка:** Actions → **Deploy 7thserpent.com** → Run workflow — в окне два поля: «SERPENT_FIRST — первая выкладка…»
и «SERPENT_DOMAIN_BOUND — домен привязан, согласен…», оба `off`.

### 2. Удалить заглушку в `www`

Файловый менеджер панели → `7thserpent.com/www` → удалить всё, что положил хостер: `index.html` заглушки и файлы рядом
с ним, если есть. Служебные папки `.well-known/` и `cgi-bin/`, если есть, — не трогать.

Почему: у заглушки нет `canonical` https://www.7thserpent.com/ — сторож `index.html` её не пропустит; непустой каталог без
нашей сборки не пропускает сторож папки (`mirror --delete` стёр бы его).

**Проверка:** в папке `www` пусто (или только `.well-known/`, `cgi-bin/`). Домен до выкладки ответит ошибкой 403 или
пустой страницей — это нормально, до шага 3 несколько минут. Сертификат уже есть (замер 2026-09-29): https по обоим
именам открывается без предупреждения — если браузер предупредит, выпустите Let's Encrypt в панели для обоих имён
**до** шага 3 (`.htaccess` сразу поведёт всех на https).

### 3. Первая выкладка — вручную

Actions → **Deploy 7thserpent.com** → **Run workflow** → ветка `main`, **`SERPENT_FIRST` = `on`**,
**`SERPENT_DOMAIN_BOUND` = `on`** → Run.

Что сделает робот: проверит секреты, заберёт корпус, соберёт сайт со всеми гейтами и сторожами, проверит папку,
`index.html` и то, что лежит внутри папок, решит, первая ли выкладка, спросит домен — и, раз вход
`SERPENT_DOMAIN_BOUND` = `on`, напечатает, что отвечают оба имени, и **не остановится, если оба отвечают с этого
хоста**; сверит сборку CI со списком, принятым в сессии 23 (`gates/sborka-prinyataya.json`, сборка `2f64543`: 165 файлов,
sha256 — после нормализации значений `data-astro-cid` ядра и хешей имён CSS), выложит файлы — главную последней —
и пересчитает их на сервере.

**Проверка:** зелёная галочка; в журнале:
- «папка робота: пустой корень» (или «свежий каталог хостера — служебные папки …»);
- «глубина: внутри папок сайта чужого нет»;
- «первая выкладка: да — вход SERPENT_FIRST=on»;
- «www.7thserpent.com: ОТВЕЧАЕТ — ответ …» и «7thserpent.com: ОТВЕЧАЕТ — ответ …», затем «первая выкладка: владелец
  согласен, что домен привязан (вход SERPENT_DOMAIN_BOUND = on, П108), оба имени отвечают с этого хоста … — выкладка идёт»;
- «сборка CI = принятая (2f64543): 165 файлов, sha256 те же; побайтно иных … — только значения data-astro-cid…»;
- «на сервере ровно dist/: 165 файлов, ключевые на месте».

После галочки https://www.7thserpent.com/ — наша главная; https://www.7thserpent.com/privacy/ — адрес
`contact@7thserpent.com` в ряду 07.

**Сторож домена со входом остановит выкладку**, если домен отвечает не так, как привязанный к этому хостеру: ошибка
сертификата (выпустите Let's Encrypt в панели для обоих имён), одно из имён не отвечает или не привязано, домен ведёт
на чужой хост или показывает чужой сайт, петля редиректов (переадресация между www и голым именем в панели спорит
с нашим `.htaccess`). Причина — в строке `СТОП`.

**Повтор — только новым запуском.** После любого красного креста запускайте снова кнопкой **Run workflow** с обоими
входами `on`. «Re-run jobs» согласия не несёт: вход действует только в первой попытке запуска — так повтор старого
запуска первой выкладки никогда не откатит живой сайт. На повторе сторож домена остановится со словами «новый запуск
кнопкой Run workflow».

**Красный крест** — робот остановился и сказал почему; пришлите мне строку `СТОП` (журнал я читаю сам, репозиторий
публичный). До шага выкладки сервер не тронут. Красная «сборка CI не равна принятой» — сервер не тронут, в журнале —
список сборки CI для разбора: разница сборки Linux и Windows, которую нормализация не покрывает; решаем вместе. Сборка
упала раньше, на гейте знака, — та же причина (иконки перерисовываются через `sharp`).

### 5. Переменные выкладки — только после зелёного `live:check`

Settings → Secrets and variables → Actions → вкладка **Variables** → New repository variable:
**`SERPENT_DEPLOY` = `on`** (выкладка по push в `main`), **`SERPENT_LIVE` = `on`** (`live:check` после каждой выкладки).

**Проверка:** две переменные в списке Variables; следующий push в `main` по файлам сайта — прогон со строкой «домен
отвечает: выкладка обновит живой сайт» и зелёным `live:check`.

Позже, если сайт уберёт файл первого уровня (например, старую картинку в корне), выкладка остановится со строкой «рядом
с нашей сборкой записи, которых нет ни в этой сборке, ни в карте сайта прежней выкладки (… имя …)»: сервер не тронут;
если имя — наш старый файл, удалите его в файловом менеджере панели и запустите выкладку снова.

### 6. Кеш статики в панели

Статику (CSS, шрифты, картинки, иконки) у этого хостера отдаёт nginx, а не Apache: `.htaccess` на неё не действует,
поэтому правил статики в нём нет (бэклог 60 п. 11). В панели — правило кеша:
- `/_astro/*` — долгий кеш (год): в именах этих файлов хеш содержимого, правка меняет имя;
- **иконки без хеша в имени** — `/favicon.ico`, `/favicon.svg`, `/favicon-16x16.png`, `/favicon-32x32.png`,
  `/icon-192.png`, `/apple-touch-icon.png` — **короткий** кеш (день или меньше): иначе правка знака дойдёт до вернувшихся
  читателей через год.

**Проверка:** в браузере — DevTools → Network → `favicon.svg` → заголовок `Cache-Control` без `max-age=31536000`.

**Проверка:** свойство «Подтверждено»; у карты статус «Успешно», найдено 17 адресов (все страницы, кроме `/404/`).
